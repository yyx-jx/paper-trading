# 服务更新以及数据回滚

本文档用于远程主机 `<PRODUCTION_HOST>` 上的后端服务更新、数据库迁移、验收和回滚。对外服务端口为 `10001`，默认服务目录为 `/srv/p-t/app`。

本文档不记录 SSH 密码、JWT、数据库密码或任何 `.env.production` 真实密钥。执行命令时由操作者在终端或 SSH 客户端中输入凭据。

## 1. 核心原则

- 先备份，再迁移，再启动。
- 优先做代码回滚；只有 schema 或数据已经被新版本改写且旧代码不能兼容时，才做数据库恢复。
- 数据库恢复会回到备份时间点，备份之后产生的新订单、持仓、日志都会被覆盖。
- 禁止在生产环境执行 `docker compose down -v`。
- 禁止无备份执行 `db:migrate`、`db:restore` 或任何生产数据修改命令。
- 禁止直接 `DROP TABLE`、`DROP COLUMN`、`TRUNCATE` 或无条件 `DELETE` 生产数据。

## 2. 本次数据兼容说明

当前服务端期望迁移版本为：

```text
EXPECTED_SCHEMA_MIGRATION_ID=000005
```

`000005_position_buy_order_lots.sql` 是兼容式迁移，只做两件事：

```sql
ALTER TABLE positions ADD COLUMN IF NOT EXISTS buy_order_id TEXT;

CREATE INDEX IF NOT EXISTS idx_positions_buy_order_id
  ON positions(buy_order_id);
```

这类变更不会删除旧数据，也不会强制改写旧记录。新版本启动后会读取旧持仓，并尝试把旧的“按方向聚合 open position”拆成“按买单逐笔 lot”的 position。这个拆分是保守逻辑：

- 只处理仍然 `open` 且没有 `buy_order_id` 的旧持仓。
- 如果同一用户、同一轮次、同一方向已经存在新的 lot 持仓，则跳过旧聚合持仓。
- 如果旧持仓有锁定数量 `lockedQty`，则跳过，避免破坏正在卖出的状态。
- 只有当旧持仓数量和 `order_lifecycle_logs.remainingTokenQty` 汇总数量完全匹配时，才会自动拆分。
- 如果数量不匹配，会记录 skip 日志，不会强行改写。

因此，升级前必须先确认迁移已应用；升级后要检查日志中是否出现 `skipped legacy position lot rebuild`。如果出现 skip，说明有历史数据需要人工核对，不应继续做大规模交易验证。

## 3. 升级前本地检查

在本地仓库确认当前分支和提交：

```bash
git switch deploy
git status --short --branch
git log --oneline -3 --decorate
git rev-parse deploy
```

推荐至少运行这些检查：

```bash
npm run typecheck
npm run test:trading
npm run test:regression
npm run test:deployment-readiness
npm run test:migration-safety
npx tsx scripts/db-migrate.ts check
```

如果要打包服务端 release：

```bash
npm run package:release
```

如果要打包临时 HTTP 生产客户端：

```bash
ALLOW_INSECURE_PROD_HTTP=true VITE_API_BASE_URL=http://<PRODUCTION_HOST>:10001 npm run package:win:prod
```

## 4. 远程升级前检查

建议在 Git Bash、WSL 或 Linux/macOS shell 中执行以下命令。不要把密码写进命令或脚本。

确认远程目录存在：

```bash
ssh root@<PRODUCTION_HOST> "ls -la /srv/p-t/app && test -f /srv/p-t/app/.env.production"
```

确认生产环境迁移守卫配置：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && grep -E '^(SERVER_REQUIRE_MIGRATIONS|EXPECTED_SCHEMA_MIGRATION_ID|SERVER_STRICT_PERSISTENCE)=' .env.production"
```

期望看到：

```text
SERVER_REQUIRE_MIGRATIONS=true
EXPECTED_SCHEMA_MIGRATION_ID=000005
SERVER_STRICT_PERSISTENCE=true
```

如果 `EXPECTED_SCHEMA_MIGRATION_ID` 不是 `000005`，先在远程 `.env.production` 中修正后再继续。

确认容器状态：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"
```

确认当前服务健康状态：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

如果外部 `curl` 不通，也可以从远程主机本机检查：

```bash
ssh root@<PRODUCTION_HOST> "curl -f http://127.0.0.1:10001/api/health/live && curl -f http://127.0.0.1:10001/api/health/ready"
```

## 5. 远程代码快照

每次升级前都先保存当前 `/srv/p-t/app`。记录输出里的时间戳，后续代码回滚会用到。

```bash
ssh root@<PRODUCTION_HOST> 'ts=$(date +%Y%m%d_%H%M%S); mkdir -p /srv/p-t/rollback/$ts; cp -a /srv/p-t/app /srv/p-t/rollback/$ts/app; echo "ROLLBACK_TS=$ts"'
```

确认快照存在：

```bash
ssh root@<PRODUCTION_HOST> "ls -la /srv/p-t/rollback/<timestamp>/app"
```

## 6. 数据库备份

在远程服务目录执行数据库备份：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:backup"
```

备份脚本会在容器内输出类似：

```text
Backup created: backups/btc_paper_trading_YYYYMMDD_HHMMSS.dump
```

记录这个文件名。因为 compose 把 `backups` volume 挂载到 app-server 的 `/app/backups`，数据库恢复时使用：

```text
BACKUP_FILE=/app/backups/<backup>.dump
```

校验备份文件和 sha256：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server sh -lc 'ls -lh /app/backups && sha256sum -c /app/backups/<backup>.dump.sha256'"
```

## 7. 上传新服务端代码

如果使用 release 包上传，先在远程创建目录：

```bash
ssh root@<PRODUCTION_HOST> "mkdir -p /srv/p-t/app /srv/p-t/releases /srv/p-t/rollback"
```

上传 release 服务端内容：

```bash
rsync -av --delete -e "ssh" release/<release>/server/ root@<PRODUCTION_HOST>:/srv/p-t/app/
```

上传后不要覆盖远程 `.env.production` 的真实密钥。如果 release 包内不包含 `.env.production`，这是正确状态。

确认关键文件存在：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && test -f docker-compose.deploy.yml && test -f db/migrations/000005_position_buy_order_lots.sql && test -f package.json"
```

## 8. 迁移数据库

先检查 compose 配置：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production config >/tmp/p-t-compose-config.out && tail -n 20 /tmp/p-t-compose-config.out"
```

确保 PostgreSQL 和 Redis 已启动：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d postgres redis"
```

执行迁移：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:migrate"
```

检查迁移状态：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:status"
```

期望 `000005_position_buy_order_lots.sql` 显示 `applied`。

可选的只读 schema 校验：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec -T postgres psql -U paper_trading -d paper_trading -c \"SELECT column_name FROM information_schema.columns WHERE table_name='positions' AND column_name='buy_order_id';\""
```

## 9. 启动新服务

启动或重建服务：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"
```

查看状态：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"
```

查看 app-server 日志：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server"
```

重点关注：

```text
Required migration 000005 is not applied
schema_migrations is missing
skipped legacy position lot rebuild
PostgreSQL is unavailable
Write blocked
```

出现前两个迁移错误时，说明迁移没有正确应用，先不要继续验收交易功能。

## 10. 升级后验收

外部健康检查：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

远程容器健康检查：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"
```

业务 smoke 清单：

- 登录测试账号。
- 确认行情 WS 持续刷新。
- 确认用户 WS 能刷新余额、持仓、订单。
- 小金额买入一笔。
- 对刚买入的订单执行逐笔卖出。
- 再买入多笔后，测试左侧持仓面板平仓。
- 测试反手按钮在可买入场景下正常执行。
- 检查下单时倒计时不应明显卡住后一次跳十几秒。
- 检查日志页面仍能查询交易日志。

如果 smoke 失败，先保存日志：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && mkdir -p /srv/p-t/rollback/<timestamp>/logs && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --no-color app-server matching-service > /srv/p-t/rollback/<timestamp>/logs/compose-services.log"
```

## 11. 代码回滚

当新代码启动失败、健康检查失败、但数据库仍可被旧代码兼容时，优先代码回滚。

停止业务服务：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production stop app-server matching-service caddy"
```

恢复旧代码目录：

```bash
ssh root@<PRODUCTION_HOST> "rm -rf /srv/p-t/app && cp -a /srv/p-t/rollback/<timestamp>/app /srv/p-t/app"
```

启动旧代码：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"
```

验收旧代码：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

## 12. 数据库回滚

只有在这些情况下才做数据库恢复：

- 新版本已经写入旧代码无法读取的数据形态。
- 代码回滚后服务仍因为 schema 或数据内容无法启动。
- 业务确认可以接受丢失备份时间点之后产生的新交易数据。

先停止业务写入：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production stop app-server matching-service caddy"
```

执行数据库恢复：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && BACKUP_FILE=/app/backups/<backup>.dump APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:restore"
```

恢复代码目录到与该数据库备份对应的版本：

```bash
ssh root@<PRODUCTION_HOST> "rm -rf /srv/p-t/app && cp -a /srv/p-t/rollback/<timestamp>/app /srv/p-t/app"
```

重新启动：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"
```

再次验收：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

## 14. 快速检查清单

升级前：

- 本地 `deploy` 分支干净。
- 本地测试通过。
- 远程 `.env.production` 使用 `EXPECTED_SCHEMA_MIGRATION_ID=000005`。
- 远程代码快照已保存。
- 数据库备份已生成并通过 sha256 校验。
- 已记录 `<timestamp>` 和 `<backup>.dump`。

升级中：

- `docker compose config` 成功。
- `db:migrate` 成功。
- `db:status` 显示 `000005` applied。
- `up -d --build` 成功。

升级后：

- `/api/health/live` 成功。
- `/api/health/ready` 成功。
- app-server 日志无迁移错误。
- 交易 smoke 通过。
- 未出现异常的 `skipped legacy position lot rebuild`。

回滚时：

- 先停业务服务。
- 优先恢复代码。
- 只有必要时恢复数据库。
- 数据库恢复前再次确认会覆盖备份之后的新交易数据。
