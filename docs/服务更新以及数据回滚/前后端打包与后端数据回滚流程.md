# 前后端打包与后端数据回滚流程

本文用于指导用户在保留数据库回滚能力的前提下，完成前端客户端打包、后端 release 打包、远程后端服务更新和数据恢复。示例远程主机为 `<PRODUCTION_HOST>`，服务端口为 `10001`，远程服务目录为 `/srv/p-t/app`。

> 不要把 SSH 密码、JWT、数据库密码或 `.env.production` 真实密钥写入文档、脚本或 Git 提交。

## 1. 本地打包前检查

| 步骤 | 目的 | 命令 | 通过标准 |
| --- | --- | --- | --- |
| 切换部署分支 | 确认使用部署代码 | `git switch deploy` | 当前分支为 `deploy` |
| 查看工作区 | 避免把未知改动打进包 | `git status --short --branch` | 只包含确认要发布的改动 |
| 类型检查 | 检查前后端 TypeScript | `npm run typecheck` | 命令退出码为 `0` |
| 交易回归 | 检查交易主流程 | `npm run test:trading && npm run test:regression` | 两个命令都通过 |
| 部署检查 | 检查生产配置和 Electron 配置 | `npm run test:deployment-readiness && npm run test:electron-config` | 两个命令都通过 |
| 迁移检查 | 检查迁移文件顺序和安全性 | `npm run test:migration-safety && npx tsx scripts/db-migrate.ts check` | 显示迁移检查成功 |

## 2. 前端生产客户端打包

| 步骤 | 目的 | PowerShell 命令 | 说明 |
| --- | --- | --- | --- |
| 清理代理变量 | 避免用户电脑代理影响打包和连接 | `Remove-Item Env:HTTP_PROXY,Env:http_proxy,Env:HTTPS_PROXY,Env:https_proxy,Env:ALL_PROXY,Env:all_proxy,Env:UPSTREAM_PROXY_URL -ErrorAction SilentlyContinue` | 打包前执行一次 |
| 设置免代理 | 强制本次打包不走系统代理 | `$env:NO_PROXY='*'; $env:no_proxy='*'` | Electron 主进程也会启用 `no-proxy-server` |
| 设置生产地址 | 指向远程 Caddy 服务 | `$env:ALLOW_INSECURE_PROD_HTTP='true'; $env:VITE_API_BASE_URL='http://<PRODUCTION_HOST>:10001'` | 当前是临时 HTTP 生产客户端 |
| 打包客户端 | 生成 Windows 安装包 | `npm run package:win:prod` | 输出到 `deploy/windows-production/` |
| 校验产物 | 确认带版本号安装包存在 | `Get-ChildItem deploy/windows-production` | 应看到 `BTC Paper Trading Setup 0.1.0.exe` |
| 记录哈希 | 方便用户校验文件完整性 | `Get-FileHash -Algorithm SHA256 'deploy/windows-production/BTC Paper Trading Setup 0.1.0.exe'` | 保存 SHA256 值 |

前端生产包的运行方式是：渲染层访问本机 `http://127.0.0.1:18787`，Electron 主进程在本机启动代理并转发到 `http://<PRODUCTION_HOST>:10001`。这样可以降低用户电脑系统代理对连接的影响。

## 3. 后端 release 打包

| 步骤 | 目的 | 命令 | 产物 |
| --- | --- | --- | --- |
| 构建 release | 打包可上传的后端服务目录 | `npm run package:release` | `release/P_T_<version>_<timestamp>/server/` |
| 检查敏感文件 | 避免把真实环境变量打进包 | `rg -n "JWT_SECRET|POSTGRES_PASSWORD|DATABASE_URL" release/P_T_<version>_<timestamp>/server` | 只允许示例占位符，不允许真实密钥 |
| 确认关键文件 | 确认部署所需文件齐全 | `Test-Path release/P_T_<version>_<timestamp>/server/docker-compose.deploy.yml` | 返回 `True` |
| 确认迁移文件 | 确认新 schema 迁移包含在包里 | `Test-Path release/P_T_<version>_<timestamp>/server/db/migrations/000005_position_buy_order_lots.sql` | 返回 `True` |

## 4. 远程部署前保护

| 步骤 | 目的 | 命令 | 必须记录 |
| --- | --- | --- | --- |
| 验证 SSH | 确认可以免密连接远程 | `ssh -o BatchMode=yes root@<PRODUCTION_HOST> "hostname && whoami"` | 主机名和用户 |
| 验证服务健康 | 确认当前服务状态 | `curl -f http://<PRODUCTION_HOST>:10001/api/health/ready` | 返回 `ok:true` |
| 创建代码快照 | 允许代码回滚 | `ssh root@<PRODUCTION_HOST> 'ts=$(date +%Y%m%d_%H%M%S); mkdir -p /srv/p-t/rollback/$ts; cp -a /srv/p-t/app /srv/p-t/rollback/$ts/app; echo ROLLBACK_TS=$ts'` | `ROLLBACK_TS` |
| 创建数据库备份 | 允许数据回滚 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:backup"` | `<backup>.dump` |
| 校验备份 | 确认备份文件完整 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server sh -lc 'ls -lh /app/backups && sha256sum -c /app/backups/<backup>.dump.sha256'"` | `OK` |

## 5. 后端服务更新

| 步骤 | 目的 | 命令 | 注意事项 |
| --- | --- | --- | --- |
| 上传 release | 把新后端代码放到远程 release 目录 | `scp -r release/P_T_<version>_<timestamp>/server root@<PRODUCTION_HOST>:/srv/p-t/releases/P_T_<version>_<timestamp>/` | 不上传真实 `.env.production` |
| 停止写入服务 | 防止部署中产生新写入 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production stop app-server matching-service caddy"` | 不停止 postgres/redis |
| 保留生产环境文件 | 保存远程真实配置 | `ssh root@<PRODUCTION_HOST> "cp -a /srv/p-t/app/.env.production /tmp/p-t.env.production"` | 后续复制回新目录 |
| 替换代码目录 | 切换到新 release | `ssh root@<PRODUCTION_HOST> "rm -rf /srv/p-t/app && cp -a /srv/p-t/releases/P_T_<version>_<timestamp>/server /srv/p-t/app && cp -a /tmp/p-t.env.production /srv/p-t/app/.env.production"` | 禁止删除 Docker volumes |
| 更新迁移目标 | 让新服务要求最新 schema | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && sed -i 's/^EXPECTED_SCHEMA_MIGRATION_ID=.*/EXPECTED_SCHEMA_MIGRATION_ID=000005/' .env.production"` | 必须是 `000005` |
| 执行迁移 | 升级数据库 schema | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:migrate"` | 先备份再迁移 |
| 查看迁移状态 | 确认迁移已应用 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:status"` | `000005` 显示 applied |
| 启动服务 | 重建并启动新服务 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"` | 禁止 `docker compose down -v` |

## 6. 数据恢复与回滚

| 场景 | 使用方式 | 命令 | 风险 |
| --- | --- | --- | --- |
| 只回滚代码 | 新代码启动失败但旧代码兼容当前库 | `ssh root@<PRODUCTION_HOST> "rm -rf /srv/p-t/app && cp -a /srv/p-t/rollback/<ROLLBACK_TS>/app /srv/p-t/app && cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"` | 不丢失备份后的新交易数据 |
| 恢复数据库 | 当前库需要回到备份时间点 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && BACKUP_FILE=/app/backups/<backup>.dump APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:restore"` | 会覆盖备份时间点之后的新订单、持仓和日志 |
| 恢复后重跑迁移 | 用旧备份恢复到新服务 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:migrate"` | 必须确认 `db:status` |
| 恢复后启动 | 恢复完成后重新启动服务 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build"` | 启动后立即检查健康接口 |

## 7. 部署后验收

| 验收项 | 命令或操作 | 通过标准 |
| --- | --- | --- |
| Live 健康 | `curl -f http://<PRODUCTION_HOST>:10001/api/health/live` | HTTP 200 |
| Ready 健康 | `curl -f http://<PRODUCTION_HOST>:10001/api/health/ready` | `ok:true`，`schemaMigration:"000005"` |
| 容器状态 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"` | app-server、matching-service、postgres、redis healthy |
| 日志扫描 | `ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server matching-service"` | 无 migration missing、Write blocked、Unhandled 等关键错误 |
| 客户端连接 | 安装 `BTC Paper Trading Setup 0.1.0.exe` 并登录 | 行情、用户数据、订单和持仓正常刷新 |
| 交易 smoke | 小额买入、逐笔卖出、平仓、反手 | 订单状态和持仓变化符合预期 |

## 8. 禁止操作

| 禁止项 | 原因 |
| --- | --- |
| `docker compose down -v` | 会删除 PostgreSQL、Redis、logs、backups 等持久化 volume |
| 无备份执行 `db:restore` | 选错备份会难以恢复 |
| 直接 `DROP TABLE` / `TRUNCATE` 生产表 | 会绕过可回滚流程 |
| 把密码写入 Markdown 或 Git | 会造成生产凭据泄露 |
| 用占位符地址打生产客户端 | 用户客户端会连不到真实服务 |
