# 高级运维故障排查手册

本文档面向具备 SSH、Docker Compose、基础网络诊断能力的高级运维，用于远程生产环境故障定位、处置、回滚和证据保留。当前生产对外入口仍为 HTTP `10001`，部署主目录为 `/srv/p-t/app`。

PS：文章中PRODUCTION_HOST是服务器的IP，服务器的IP最好不要明文外传给任何人，外传出去很危险。


## 快速使用目录

### 先判断是哪一类故障

- `10001` 端口不通：看 `3.1`
- 服务已经启动(live)但 `ready`（未就绪） 失败：看 `3.2`
- `app-server`重启或者启动失败：看 `3.3`
- `matching-service` 没有提供服务：看 `3.4`
- PostgreSQL 没有提供服务：看 `3.5`
- Redis 没有提供服务：看 `3.6`
- 客户端在线异常、行情卡顿、状态跳变：看 `3.7`
- 数据源超时或市场不更新：看 `3.8`
- 日志写入异常或日志导出不完整：看 `3.9`

### 先跑这几个通用检查

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl http://<PRODUCTION_HOST>:10001/api/health/ready
curl http://<PRODUCTION_HOST>:10001/api/metrics
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 matching-service
```

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec matching-service sh -lc 'tail -n 50 /app/data/logs/matching-snapshots.jsonl'
```

### 遇到这些情况先不要误判

- 公网 `/metrics` 返回 `404`：正常
- `degraded`：是降级，不等于完全不可用（degraded一般是现在系统内一些数据的延时超过了设置的阈值，所以采用降级来提高服务，如果延时回复就立马回到正常的服务中）
- `ready=503`：说明服务没有准备好，不能只看 `live`
- 生产环境禁止 `docker compose down -v`

### 要重启前先做什么（注意是重启前！！）

- 先记录故障时间
- 先保存 `docker compose ps`
- 先保存相关容器最近 200 行日志
- 先保存 `live`、`ready`、`metrics` 返回结果

### 什么时候必须升级研发

- `EXPECTED_SCHEMA_MIGRATION_ID` 不匹配
- `db:migrate` 失败
- JSONL 持续写失败或持续丢记录
- 上游数据源长期 `stale` 或 `reconnecting`
- 怀疑数据库、日志、备份损坏
- 需要做数据库恢复

### 1.3 Docker 服务与持久化

生产编排涉及以下容器：

```text
caddy               反向代理，对外暴露 10001
app-server          主服务进程，处理 API、WebSocket、认证、业务编排
matching-service    撮合服务进程，处理撮合、订单簿、成交相关逻辑
postgres
redis
prometheus   (monitoring profile 启用时)
grafana      (monitoring profile 启用时)
```

关键持久化卷：

```text
pgdata / app_pgdata         PostgreSQL 数据
redisdata / app_redisdata   Redis 数据
logs / app_logs             JSONL 日志
backups / app_backups       数据库备份
```

说明：

- `app-server` 和 `matching-service` 的 JSONL 日志目录在容器内是 `/app/data/logs`。
- 生产数据库备份目录在 `app-server` 容器内是 `/app/backups`。
- 卷在 `docker-compose.deploy.yml` 中声明为 `pgdata`、`redisdata`、`logs`、`backups`，实际 `docker volume ls` 中通常会带项目名前缀。

### 1.4 各类日志位置与用途

先区分两类日志：

- 容器运行日志：通过 `docker compose logs` 查看，适合排查启动失败、健康检查失败、连接报错、进程退出。
- 应用 JSONL 日志：位于容器内 `/app/data/logs`，适合排查交易、撮合、行为、订单簿快照等业务问题。

容器运行日志查看方式：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 caddy
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 matching-service
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 postgres
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 redis
```

应用 JSONL 日志位置：

```text
/app/data/logs/audit-events.jsonl
/app/data/logs/behavior-action-logs.jsonl
/app/data/logs/matching-events.jsonl
/app/data/logs/matching-snapshots.jsonl
```

各文件含义：

- `audit-events.jsonl`：审计日志，重点看交易、撤单、结算、redeem、延迟事件。
- `behavior-action-logs.jsonl`：训练日志，重点看用户动作、市场上下文、成交与结算结果。
- `matching-events.jsonl`：独立 `matching-service` 事件流，适合调试撮合执行问题。
- `matching-snapshots.jsonl`：独立 `matching-service` 订单簿快照，适合回看盘口状态和撮合现场。

快速查看 JSONL 日志：

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec app-server sh -lc 'ls -lah /app/data/logs'
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec app-server sh -lc 'tail -n 50 /app/data/logs/audit-events.jsonl'
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec app-server sh -lc 'tail -n 50 /app/data/logs/behavior-action-logs.jsonl'
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec matching-service sh -lc 'tail -n 50 /app/data/logs/matching-events.jsonl'
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec matching-service sh -lc 'tail -n 50 /app/data/logs/matching-snapshots.jsonl'
```

常见查看建议：

- 服务起不来：先看 `docker compose logs app-server` 或 `docker compose logs matching-service`。
- 入口不通：先看 `docker compose logs caddy`。
- 数据库问题：先看 `docker compose logs postgres`。
- 缓存问题：先看 `docker compose logs redis`。
- 订单、成交、撤单、结算异常：先看 `audit-events.jsonl` 和 `matching-events.jsonl`。
- 行情或盘口状态异常：先看 `matching-snapshots.jsonl`，再结合 `app-server` 日志一起看。

## 2. 故障分层排查流程

故障排查必须按层次进行，避免一上来直接重启或恢复数据。推荐顺序是：

1. 先确认入口是否可达。
2. 再确认容器是否健康。
3. 再确认容器内依赖和应用状态。
4. 最后确认外部数据源是否进入降级或重连。

### 2.1 第一层：入口可达性，即验证系统是否正常启动（不保证系统内的业务服务正常处理）

先在运维本机执行：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

正常结果：

- `/api/health/live` 返回 HTTP 200，且 `ok: true`。
- `/api/health/ready` 返回 HTTP 200，且 `ok: true`。

异常结果：

- TCP 连接失败、超时、连接重置，说明入口层或主机网络层有问题。
- `live` 正常但 `ready` 返回 503，说明入口通，但应用未达到可服务状态。

注意：

- 公网访问 `/metrics` 返回 `404` 是预期行为，不算故障。
- `deploy/Caddyfile` 默认显式拦截公网 `/metrics`。

如公网无法判断，可在远程主机本机复查：

```bash
ssh root@<PRODUCTION_HOST> "curl -f http://127.0.0.1:10001/api/health/live"
ssh root@<PRODUCTION_HOST> "curl -f http://127.0.0.1:10001/api/health/ready"
```

### 2.2 第二层：容器状态

进入远程部署目录：

```bash
ssh root@<PRODUCTION_HOST>
cd /srv/p-t/app
```

统一使用以下环境参数执行：

```bash
export APP_ENV_FILE=.env.production
```

检查容器状态：

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps
```

检查关键日志：

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 caddy
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 matching-service
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 postgres
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 redis
```

正常结果：

- `caddy`、`app-server`、`matching-service`、`postgres`、`redis` 都处于 `Up`。
- `app-server` 和 `matching-service` 显示健康状态。

异常结果：

- `caddy` 未运行：入口层故障。
- `app-server` 未运行或不健康：应用层故障。
- `matching-service` 未运行或不健康：撮合层故障。
- `postgres` 或 `redis` 未运行、不健康：依赖层故障。

### 2.3 第三层：容器内健康与依赖

从容器内部确认服务：

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec app-server wget -qO- http://127.0.0.1:8787/api/health/ready
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec matching-service wget -qO- http://127.0.0.1:8788/health
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec postgres pg_isready -U paper_trading -d paper_trading
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec redis redis-cli ping
```

正常结果：

- `app-server` 返回 `ok: true`。
- `matching-service` 返回健康响应。
- `pg_isready` 返回 `accepting connections`。
- `redis-cli ping` 返回 `PONG`。

异常定位：

- `app-server` 失败但 `postgres`、`redis` 正常：应用本身或迁移状态有问题。
- `matching-service` 失败：撮合服务异常，可能影响下单、撤单、成交。
- `pg_isready` 失败：数据库不可用。
- `redis-cli ping` 失败：缓存或会话相关功能可能异常。

### 2.4 第四层：上游数据源与降级状态

应用层和依赖层正常后，再看实时数据源：

```bash
curl http://<PRODUCTION_HOST>:10001/api/health/ready
curl http://<PRODUCTION_HOST>:10001/api/metrics
```

需要重点关注 `sources` 或 `externalSources` 中的状态值：

```text
healthy       正常
degraded      已降级，但仍可能部分可用
stale         数据陈旧
reconnecting  正在重连
disabled      明确禁用
```

说明：

- `degraded` 不等于完全不可用，常见于 Binance、Chainlink、Polymarket 已切换到兜底路径。
- `stale` 和 `reconnecting` 持续存在，通常意味着上游连通性或代理有问题。

生产环境重点检查：

```bash
grep -E '^UPSTREAM_PROXY_URL=' /srv/p-t/app/.env.production
```

同时排查：

- 服务器到 Binance、Polymarket、Chainlink 的外网连通性。
- 代理是否可用。
- 安全组、出口防火墙、SD-WAN、路由是否变更。

## 3. 按故障现象分类处理

本节按“现象、检查命令、正常结果、异常结果、处理动作、升级条件”组织。

### 3.1 现象：`10001` 端口不通

检查命令：

```bash
curl -v http://<PRODUCTION_HOST>:10001/api/health/live
ssh root@<PRODUCTION_HOST> "ss -lntp | grep 10001 || netstat -lntp | grep 10001"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 caddy"
```

正常结果：

- 远程主机监听 `10001`。
- `caddy` 容器处于 `Up`。

异常结果：

- 主机未监听 `10001`：Caddy 未起或端口映射异常。
- 监听存在但外部仍不通：防火墙、安全组、路由或运营商网络问题。

处理动作：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d caddy
```

如仍失败，继续排查：

- 主机防火墙是否放行 `10001/tcp`。
- 云安全组是否放行 `10001/tcp`。
- `deploy/Caddyfile` 是否被误改。

升级研发条件：

- `caddy` 正常但仍无法暴露服务。
- `10001` 对内正常、对外异常且排除网络策略后仍未恢复。

### 3.2 现象：`live` 正常但 `ready` 失败

检查命令：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl http://<PRODUCTION_HOST>:10001/api/health/ready
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server"
```

正常结果：

- `ready` 返回 `ok: true`。

异常结果：

- `ready` 返回 HTTP 503。
- 返回体中的 `persistence`、`matchingService`、`sources` 显示某个依赖不满足就绪条件。

处理动作：

- 优先查看 `app-server` 日志中的迁移、数据库、Redis、撮合服务错误。
- 再按 3.3、3.4、3.5、3.6 继续细分。

升级研发条件：

- `app-server` 无明显日志但 `ready` 长时间 503。
- 返回字段无法解释当前就绪失败原因。

### 3.3 现象：`app-server` 起不来或反复重启

检查命令：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && grep -E '^(SERVER_REQUIRE_MIGRATIONS|EXPECTED_SCHEMA_MIGRATION_ID|SERVER_STRICT_PERSISTENCE|MATCHING_SERVICE_URL|NODE_ENV|DEPLOY_ENV)=' .env.production"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:status"
```

正常结果：

- `SERVER_REQUIRE_MIGRATIONS=true`
- `EXPECTED_SCHEMA_MIGRATION_ID=000005`
- `db:status` 显示目标迁移已应用。

异常结果：

- 出现以下日志之一：

```text
[store] SERVER_REQUIRE_MIGRATIONS=true but schema_migrations is missing. Run npm run db:migrate first.
[store] Required migration 000005 is not applied. Run npm run db:migrate first.
PostgreSQL is unavailable
Write blocked
```

处理动作：

1. 先确认 `postgres` 正常。
2. 若是迁移缺失，先备份数据库，再执行迁移：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:backup
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:migrate
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:status
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d app-server
```

3. 若是配置错误，修正 `.env.production` 后重启：

```bash
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d app-server
```

升级研发条件：

- `EXPECTED_SCHEMA_MIGRATION_ID` 与发布要求不一致。
- `db:migrate` 执行失败。
- 迁移状态显示已应用，但服务仍无法启动。

### 3.4 现象：`matching-service` 不健康

检查命令：

```bash
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 matching-service"
ssh root@<PRODUCTION_HOST> "cd /srv/p-t/app && APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production exec matching-service wget -qO- http://127.0.0.1:8788/health"
```

正常结果：

- `matching-service` 容器 `Up (healthy)`。
- 内部 `/health` 正常。

异常结果：

- 容器退出、重启、健康检查失败。
- `app-server` 的 `ready` 中 `matchingService.ok=false`。

处理动作：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d matching-service
```

如依赖数据库或 Redis，先确保其健康后再重启撮合服务。

## 4. 恢复与回滚

### 4.1 低风险恢复

优先使用低风险动作：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d app-server
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d matching-service
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d postgres
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d redis
```

如需短停重启某个服务，可先采集证据再执行。

### 4.2 发布前后固定动作

每次生产更新、迁移、回滚前都先执行备份：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:backup
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:migrate
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:status
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build
```

### 4.3 代码回滚

代码回滚优先于数据回滚。

回滚前先停关键业务服务：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production stop app-server matching-service
```

用已保存的代码快照恢复：

```bash
cp -a /srv/p-t/rollback/<timestamp>/. /srv/p-t/app/
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production up -d --build
```

回滚后立即验证：

```bash
curl -f http://<PRODUCTION_HOST>:10001/api/health/live
curl -f http://<PRODUCTION_HOST>:10001/api/health/ready
```

### 4.4 数据回滚

只有在以下情况下才考虑数据库恢复：

- 新旧 schema 不兼容。
- 旧代码无法读取当前库结构。
- 已确认必须回到备份时间点。

数据库恢复会覆盖备份后的新增数据，执行前必须升级研发并确认业务影响。

恢复命令示例：

```bash
cd /srv/p-t/app
BACKUP_FILE=/app/backups/<backup>.dump APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production run --rm app-server npm run db:restore
```

### 4.5 明确禁止项

生产环境禁止：

```text
docker compose down -v
DROP TABLE / DROP COLUMN / DROP SCHEMA
TRUNCATE
无条件 DELETE 生产数据
未确认备份前直接执行 db:migrate 或 db:restore
未采集证据就重启、回滚、恢复
```

## 5. 证据采集与升级标准

### 5.1 必须保留的证据

发生故障时，至少保留以下信息：

- 故障开始时间、恢复时间、影响范围
- 是否刚发版、刚迁移、刚改代理、刚切网络
- `docker compose ps`
- 相关容器最近 200 行日志
- `/api/health/live` 返回结果
- `/api/health/ready` 返回结果
- `/api/metrics` 返回结果
- 主机磁盘空间、端口监听、关键卷状态

建议使用以下命令统一采集：

```bash
cd /srv/p-t/app
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production ps
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 caddy
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 app-server
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 matching-service
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 postgres
APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production logs --tail=200 redis
curl http://<PRODUCTION_HOST>:10001/api/health/live
curl http://<PRODUCTION_HOST>:10001/api/health/ready
curl http://<PRODUCTION_HOST>:10001/api/metrics
df -h
ss -lntp | grep 10001 || netstat -lntp | grep 10001
```

### 5.2 必须立即升级研发的情况

出现以下任一情况时，不要自行继续高风险操作，先升级研发：

- `EXPECTED_SCHEMA_MIGRATION_ID` 与发布要求不匹配
- `db:migrate` 失败
- `db:status` 与实际运行版本不一致
- JSONL 持续写失败或持续丢记录
- 上游数据源长期 `stale` 或 `reconnecting`
- 怀疑数据库、日志或备份损坏
- 需要执行数据库恢复
- 代码回滚后仍未恢复
- 现象只在高并发、批量连接、持续运行一段时间后出现





## 7. 附录：关键判断口径

- `/metrics` 公网 `404`：正常，因 Caddy 默认拦截。
- `degraded`：降级，不等于完全不可用。
- `ready=503`：说明服务暂时不满足就绪条件，不要只看 `live`。
- 先代码回滚，后数据回滚：这是默认顺序。
- `docker compose down -v`：生产禁用。
重点确认：
- `ready.ok=true`
- PostgreSQL、Redis、matching-service、app-server 全部健康
- 关键外部数据源不是长期 `stale/reconnecting`
- JSONL backlog、写失败、丢记录未持续增长
