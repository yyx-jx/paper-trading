一、结论

问题不在后端服务本身，也不是单纯的业务代码导致 CLOB 断开。

当前证据指向：云服务器的 DNS/解析链路存在污染、劫持或错误解析，导致 Polymarket 域名被解析到错误 IP。应用容器按系统 DNS 访问这些错误 IP 后，出现 TLS 证书不匹配、TCP 连接超时、WebSocket AggregateError，从而表现为 CLOB 长时间断开或降级。

七、根因判断

根因优先级：

1. 高概率：服务器 DNS 被污染、劫持或错误解析。
   证据：系统 DNS 返回错误 IP；公共 DoH 返回正确 Cloudflare IP；强制正确 IP 后 CLOB/Data API 立即恢复 HTTP 200。

2. 次高概率：当前 DNS 链路中 223.6.6.6、运营商出口或机房网络对 Polymarket 域名返回了污染结果。
   证据：resolvectl 当前 DNS Server 是 223.6.6.6，查询结果包含明显不属于 Polymarket 的 IP。

3. 低概率：后端业务代码导致连接失败。
   反证：服务 ready 正常，postgres/redis/matching 正常；容器内独立 Node fetch 不经过业务逻辑也失败；强制正确 DNS 后宿主机 curl 成功。

八、建议处理

建议先处理 DNS，再观察 CLOB 状态：

1. 把服务器 DNS 调整为干净稳定的解析方式，优先使用 DoH/DoT 或可信解析器。
2. 避免继续使用会返回污染结果的 DNS 链路；当前 223.6.6.6 返回结果不可信。
3. DNS 修改后执行：
   - resolvectl flush-caches
   - resolvectl query clob.polymarket.com
   - resolvectl query data-api.polymarket.com
   - resolvectl query gamma-api.polymarket.com
4. 确认解析结果变为：
   - 104.18.34.205
   - 172.64.153.51
   或同属 Cloudflare 的正确边缘 IP。
5. 再重启 app-server 容器，让 Node 进程重新使用正确 DNS：
   - cd /srv/p-t/app
   - APP_ENV_FILE=.env.production docker compose -f docker-compose.deploy.yml --env-file .env.production restart app-server
6. 如果机房 DNS/出口仍不稳定，给生产配置 UPSTREAM_PROXY_URL，使用稳定代理访问 Polymarket。

十、给测试的简短说法

生产后端没有挂，数据库、Redis、matching 都是 healthy。CLOB 断连的直接原因是云服务器 DNS 把 Polymarket 域名解析到了错误 IP，导致容器内直连 Polymarket 出现证书不匹配和连接超时。强制使用公共 DoH 返回的正确 Cloudflare IP 后，clob.polymarket.com 和 data-api.polymarket.com 都能返回 200。因此这是服务器 DNS/出站解析链路问题，不是后端业务服务自身问题。

十一、为什么会错误解析

追加排查时间：2026-05-13 23:34-23:37 Asia/Shanghai

进一步只读排查确认：错误解析不是 Docker、Node.js 或应用代码造成的，而是服务器 DNS 上游配置中包含了会返回污染结果的 223.6.6.6。

关键配置来源：

1. /etc/resolv.conf 指向 systemd-resolved stub：
   - /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
   - nameserver 127.0.0.53

2. systemd-resolved 的 eth0 DNS 列表：
   - DNS Servers: 1.1.1.1 8.8.8.8 223.6.6.6
   - Current DNS Server: 223.6.6.6

3. 223.6.6.6 来自 cloud-init/netplan：
   - /etc/netplan/50-cloud-init.yaml
   - /etc/cloud/cloud.cfg.d/90-installer-network.cfg
   - 这两个配置里都包含 nameservers: 1.1.1.1, 223.6.6.6

4. 服务器还有 /etc/netplan/01-netplan.yaml，里面配置了 1.1.1.1 和 8.8.8.8。
   netplan 最终合并后，eth0 得到 1.1.1.1、8.8.8.8、223.6.6.6 三个 DNS。

直接指定不同 DNS 服务器查询 Polymarket 的结果：

1. 查询 1.1.1.1：
   - gamma-api.polymarket.com -> 172.64.153.51, 104.18.34.205
   - clob.polymarket.com -> 104.18.34.205, 172.64.153.51
   - data-api.polymarket.com -> 104.18.34.205, 172.64.153.51
   - ws-subscriptions-clob.polymarket.com -> 104.18.34.205, 172.64.153.51

2. 查询 8.8.8.8：
   - gamma-api.polymarket.com -> 172.64.153.51, 104.18.34.205
   - clob.polymarket.com -> 172.64.153.51, 104.18.34.205
   - data-api.polymarket.com -> 172.64.153.51, 104.18.34.205
   - ws-subscriptions-clob.polymarket.com -> 172.64.153.51, 104.18.34.205

3. 查询 223.6.6.6：
   - gamma-api.polymarket.com -> 103.252.114.61
   - clob.polymarket.com -> 65.49.26.99
   - data-api.polymarket.com -> 157.240.2.36
   - ws-subscriptions-clob.polymarket.com -> 108.160.169.179

4. 查询本机 systemd-resolved stub 127.0.0.53：
   - gamma-api.polymarket.com -> 98.159.108.57
   - clob.polymarket.com -> 108.160.165.211
   - data-api.polymarket.com -> 157.240.2.36
   - ws-subscriptions-clob.polymarket.com -> 54.234.18.200

判断：

1. 1.1.1.1 和 8.8.8.8 在这台服务器上可以直接返回正确 Cloudflare IP，说明服务器 53 端口不是整体被透明劫持。
2. 223.6.6.6 对 Polymarket 域名返回了错误 IP，这是污染结果来源。
3. systemd-resolved 当前选中的上游是 223.6.6.6，所以应用和 Docker 容器通过 127.0.0.53 解析时会拿到错误结果。
4. 223.6.6.6 是 cloud-init/netplan 配置带入的，不是应用代码配置。

更精确的根因：

云服务器网络配置里混用了 1.1.1.1、8.8.8.8 和 223.6.6.6；其中 223.6.6.6 对 Polymarket 返回污染 DNS 结果。systemd-resolved 当前使用 223.6.6.6 并缓存其错误答案，导致 app-server 容器解析 CLOB/Gamma/Data API 到错误 IP，从而出现 TLS 证书不匹配、HTTP 超时和 WebSocket AggregateError。
